# magpie 线程池设计审核（2026-10-03）

> 本报告为修订前的历史审核，正文行号指向旧版本。2026-10-03 已按意见修订主设计、ADR 和验证计划，逐项结果见 [修复对照](review-fixes-2026-10-03.md)。以下反例保留用于回归，不代表当前骨架仍包含这些算法。

结论：总体组件划分可保留，但当前实现级骨架存在会导致重复执行、任务丢失、越界和 shutdown/join 挂死的缺陷，不能认定为设计闭环。ADR 中“核心协议成立”“无重复消费、无丢失”等结论需要撤回并重新证明。

审核范围：主设计、三个 ADR、test-plan、benchmark-plan。当前仓库没有线程池实现、构建系统或已执行的测试/benchmark 结果，本报告是设计与算法审核，不是实现验收。没有修改原设计文档。

## 验证证据及限制

依据文档骨架，在 `/private/tmp/magpie-review-20261003/repro.cpp` 中拆分暂停中的操作，构造确定性调度。使用 C++20 atomics，Clang `-O2 -Wall -Wextra -Werror` 编译并运行，七个反例检查全部通过。

同一复现程序以 ASan+UBSan 构建再次运行，输出一致且没有 sanitizer 报错。复现程序刻意只检查协议状态、容量需求和重复 id，不执行悬空指针解引用或越界写；sanitizer 通过不表示原骨架安全。

这不是实际多线程线程池测试，也没有在 macOS 上执行 Linux futex。EventCount 检查验证的是：通知已结束后，等待者仍能走到“内核比较值相等、允许睡眠”的状态；因而现有协议不能保证通知被保留。无需弱内存序、随机调度或数值回绕就可触发这些状态。

## 必须修复的缺陷

### R1：批量 steal 与连续 owner pop 会重复认领同一任务

位置：主设计 §7.1.2 `steal`（558–578 行）；ADR-001 §4.1（尤其 91 行的证明前提）。

要求：成功消费区间必须互斥，候选快照必须仍对应待消费任务。

反例：

1. 初始 `top=0, bottom=8`，任务 T0…T7。
2. thief 读取上述边界、计算 `n=4`、锁存 T0…T3，在 CAS 前暂停。
3. owner 连续 pop 并执行 T7、T6、T5、T4、T3。全部走常规分支，不更新 top；此时 `top=0, bottom=3`。
4. thief 的 `CAS(top, 0, 4)` 成功，交付 T0…T3。

T3 被重复消费，且 `top>bottom`。如果 owner 已删除 T3，thief 将持有悬空指针。即便不删除任务，该重复消费也已违反守恒。

ADR 的证明把窃取者读取的 bottom 限定为“本次 pop 前 b 或本次 pop 后 b−1”，遗漏了同一个 steal 跨越多次 pop 的情形。一次只取旧深度的一半并不能保护任意长暂停窗口。

推荐：初版改为已证明的单元素 Chase-Lev steal。需要批量接收时，在池层重复执行单元素 steal，每次成功有自己的认领点。若坚持一次 CAS 认领整批，必须使用具有独立证明的批量协议；仅 CAS 前复查 bottom 仍有“复查后 owner 再 pop”的窗口。

### R2：最后一个任务竞争失败后 bottom 恢复值错误

位置：主设计 §7.1.2 `pop` 第 549 行。

`compare_exchange_strong` 失败会修改其 expected 参数 `t`。当前代码随后执行 `bottom.store(t+1)`，使用的是修改后的值。

反例：初始 `top=0, bottom=1`。thief 先锁存唯一任务，owner 减 bottom 到 0 并读得 top=0，thief 随后 CAS 0→1 成功。owner CAS 失败后 `t=1`，当前恢复语句把 bottom 写为 2，而正确空状态应为 `top=bottom=1`。下次 pop 可能读出槽 1 的 nullptr 或旧任务指针，产生虚假任务或重复回收。

推荐：单元素协议的竞争分支使用稳定的本地索引 `b+1` 恢复 bottom，不使用会被 CAS 修改的 expected。批量协议必须先解决 R1，不能套用这一局部修复后就认定整个 deque 正确。

一手源码对照：[Taskflow BoundedWSQ](https://taskflow.github.io/taskflow/wsq_8hpp_source.html) 的 pop 使用 `bottom.store(b+1)`；其 steal 同时保留 top load 与 bottom load 之间的 SC fence。恢复值、配对屏障和完整协议需要一起核对。

### R3：overflow 固定缓冲容量证明不成立

位置：主设计 486–495、600–605、1353 行；ADR-001 §4.6。

默认 `local_deque_capacity=1024`，`BATCH_CAP=max(32,64)=64`。

反例：本地已经有 1024 个任务，全局队列也满。下一次 worker 内 submit 只调用一次 push，却会 spill 512 个旧任务；如果全部入全局失败，需要追加 512 个指针。第 65 次追加已超过 64 槽缓冲：debug 终止，release 越界。

证明中的“append 总量 ≤ 两次 drain 之间 push 总数”遗漏了上一轮已留在 deque 中的存量；一次新 push 就能迁移半个旧 deque。

推荐：overflow 与其取出缓冲必须按实际 local capacity 和最大连续 push 批次预分配并证明上界，不能继续复用接收批的 BATCH_CAP。一个可采用的保守上界是 `local_capacity + max_push_batch`：两次 drain 间可被移出的任务最多来自起始存量和新增 push，前提是入口 overflow 已被取空且协议守恒。所有相关函数的容量契约必须同步。若采用更紧上界，需要独立证明。

### R4：溢出重试循环交换后跳过任务

位置：主设计 `drain_spill_overflow` 第 287–297 行。

失败时执行 `swap(batch[i], batch[--fail])`，但 for 循环仍然执行 `++i`，被换入当前位置的任务没有被处理。

反例：`batch=[A,B], n=2`。A 入队失败后，变为 `[B,A], fail=1`，接着 i 从 0 增为 1，循环直接结束。fallback 只执行 `[fail,n)` 中的 A。B 没有入队也没有执行，而 overflow 原缓冲已被取走，导致任务丢失、pending 永不归零。

推荐：使用显式 while 游标，成功才推进 i；失败后缩短未处理区间并交换，继续处理同一 i。或者使用两个固定数组分别记录成功和失败项。验证应覆盖全部失败、首项失败、交替成功失败及尾项失败。

### R5：多个等待者可把共享 futex 字写回旧值，丢失 shutdown 唤醒

位置：主设计 `wait_registered` 第 784 行；ADR-002 §3.1/§3.3 引理 3。

反例（全部 SC，无回绕）：

1. A、B 都已注册，key=0，最后任务探测为空。
2. A 写 word=0，复查 epoch=0，通过 W5，在 futex_wait 前暂停。
3. shutdown 推进 epoch=1；即使 notify_all 同时正确写 word=1，wake 时两者仍未进入内核等待队列，wake 返回 0。
4. B 恢复，执行 W4，把共享 word 写回 0；随后 W5 读到 epoch=1，注销并返回，B 可退出。
5. A 执行 futex_wait(word,0)，值比较成功，进入睡眠；最后一次 notify_all 已完成，join 可永久等待 A。

证明只讨论同一个等待者与 notifier，没有覆盖其他等待者 W4 对已更新睡眠字的覆盖。原子与 seq_cst 消除的是 data race，不是该协议竞态。generic 版把 W4/W5/wait 与 notify 用 mutex 串行化，不能以 generic 测试通过证明 futex 版不存在该窗口。

推荐：等待者不得回写共享 generation。优先采用已有完整证明的 EventCount/Notifier；或者设计 notifier 更新的单一原子 generation，等待者只读取、复查并睡在其值上，重新证明注册/通知握手。采用 32 位 futex generation 时必须明确回绕约束；“暂停期间不可能发生 2³² 次通知”不具有无条件保证。

一手设计参考：[Taskflow AtomicNotifier](https://github.com/taskflow/taskflow/blob/master/taskflow/core/atomic_notifier.hpp)，其共享状态包含 epoch 与等待者数，等待者通过原子等待观察变化，没有将过期快照写回共享睡眠字。参考协议须整体审查，不应只移植个别内存序。

### R6：block_on_eventcount 的单次 stopping 前置检查有 TOCTOU 窗口

位置：主设计第 200–211 行、§9.1 第 955 行。

反例：worker 读 stopping=false 后暂停；控制线程 shutdown 置 true 并完成 notify_all；worker 恢复，才 prepare_wait，取得 shutdown 后的新 epoch，然后注册、full_scan 判空，复查 epoch 与 key 相等，进入睡眠。已没有后续通知。

这与 R5 独立：只需要一个等待者，也不需要旧字被覆盖。当前“关停期禁止睡眠”的检查不能覆盖读取 stopping 与正式注册之间的窗口。

推荐：把停止谓词纳入已注册后的最后检查，与 EventCount 的 epoch/wait 握手共同证明。注册后发现 stopping 必须 leave 并返回；注册后检查为 false 而 shutdown 随后发生的路径必须由 epoch 变化或 wake 覆盖。构造失败回滚同样必须置 stopping、notify_all 再 join，不能只期待线程“自然退出”。

### R7：CallerRuns 内调用 shutdown/drain 存在未覆盖的自等待

位置：主设计第 871–874、929–932 行，以及 §9.1/§9.5。

外部 CallerRuns 的 task 在 submit_task 的 Gate 生存期内运行。该 task 调用本池 shutdown 时，shutdown 等 `in_flight_submitters==0`；当前调用栈自己持有的 gate 只有 task 返回、submit_task 退出时才释放，形成自等待。该 task 调用 drain 也会等待包含自己的 pending，无法返回。

当前禁令仅检测“本池 worker”；外部 CallerRuns 没有该 worker 身份，因此遗漏上述执行上下文。worker 内 submit 触发 spill fallback 时，在持 gate 的嵌套任务里也可能遇到 shutdown 自等待。

推荐：区分 owner worker 身份与“正在执行本池任务”的上下文，用后者约束所有会等待本池自身的操作。更清晰的生命周期 API 是非阻塞停止请求与外部等待/join 分离；若保留同步 shutdown，则必须明确禁止本池任务调用，覆盖 CallerRuns、溢出 fallback、异常回调等上下文。不要简单提前释放 gate，否则外部执行与析构的 lifetime 保障会被改变。

## 其他需要补齐的设计契约

| 问题 | 证据与影响 | 建议 |
|---|---|---|
| drain 返回保证过强 | §9.3 第 979 行声称“返回前已入池的任务全部完成”；谓词读取 pending=0 后、函数真正返回前，新的 submit 可入池并尚未完成 | 保证应锚定成功观察 pending=0 的时刻；返回时集合为空只有在停止接收或调用方保证无并发提交时成立 |
| hot path 成本描述相互矛盾 | §2.1“任务 cycle 只碰本地行”被每次完成的 pending RMW 打破；内部 submit 仍操作 gate、pending、submitted、epoch 多条共享行；第 748、1218 行仍保留过时成本口径 | 写出各路径完整共享 RMW 清单，结合 cache-line ownership transfer 和吞吐归因，不把 work-stealing 直接等同于 share-nothing |
| 空任务 worker scaling 验收受全局热点约束 | T8/T1≥6.4 测到的是 allocation、MPMC、gate、pending、epoch 和执行的组合；CallerRuns 还可能把 producer 当成执行者 | 分别测提交端、worker 执行端、本地 spawn、端到端吞吐；固定 producer 资源和 rejection 配置，单列 CallerRuns 完成数；不能用增加 producer 执行量解释 worker scaling |

## 验证计划的实际缺口

现有测试名称很多，但没有已运行证据，且确定性注入点没有覆盖上述关键窗口。

应新增以下具体反例：

1. thief 锁存半批后暂停，owner 完成多次 pop，验证每个 id 恰消费一次。
2. 唯一任务的 thief CAS 成功后再放行 owner CAS，验证 top==bottom 且后续 pop 为空。
3. 默认 local capacity=1024，全局队列满，仅一次本地 push 触发半批 spill，验证暂存容量。
4. 溢出批次两项全失败，验证入队项与 fallback 项的并集恰等于输入且不相交。
5. 两个旧 key 等待者，A 停在 W5 后，B 停在 W4 前，夹入 notify_all，验证关闭后不再睡入内核。
6. worker 停在 stopping 前置检查后，控制线程完成 shutdown，再放行注册，验证有界 join。
7. 外部 CallerRuns 及本地 spill fallback 中调用生命周期 API，验证所选禁止/非阻塞语义。

测试计划 §4.2 的 `0≤bottom−top` 应限定在稳定边界：经典 Chase-Lev pop 的中间态可以有 `bottom<top`。不能对两个独立原子的任意快照强行断言；否则有效协议也会被误报。MPMC 的成功调用返回计数也可能暂时无法反映队列的线性化状态。

另外，加入弱内存模型检查（如有界模型检查器）并核对标准 Chase-Lev 的两侧屏障；TSan 全绿不能证明原子协议正确。generic backend 有额外 mutex，也不能替代 futex backend 的状态机验证。测试种子相同不保证 OS 调度相同，确定性 replay 需要记录并控制暂停点和交错，而不仅重放 op 序列。

## 推荐实施顺序与取舍

1. 撤回错误证明的“已接受/已成立”状态，修正 R1–R7，主文档和 ADR 保持一致。
2. 初版采用完整的单元素 Chase-Lev 协议和已有证明的唤醒器；全局 dequeue_bulk 可保留，因为它重复已有单元素出队，没有一次 CAS 认领可变边界的问题。
3. 拆清 deque 原语与池层调度职责，定义任务执行上下文及生命周期禁令，补构造失败回滚。
4. 以本报告的确定性反例建立回归，再进行 sanitizer、模型检查和真实 Linux benchmark。
5. 批量 steal、轻量 notify、内存序放宽均作为独立优化，只有正确性证明与性能证据同时成立才引入。

无需为这次修复引入 NUMA、任务图或 helping future 等新体系。无 helping wait、无饥饿上界、固定容量以及 CallerRuns 递归深度风险已是文档明确接受的限制；不将这些限制重复列作新发现。总体方向合理，但当前首要工作是恢复任务守恒与唤醒/关闭活性，而非继续微调性能常数。
